# Embedded Architecture Decision Rules

## 核心哲学

嵌入式软件设计的本质：**把系统中最容易变化的部分从主流程里拆出去**，降低耦合，方便扩展和维护。
六种模式分别对应六类变化点：状态变化、事件分发、算法替换、对象创建、请求封装、消息广播。

## 工程进入流程

每次进入一个工程时，按以下顺序建立上下文：

1. **寻找工程目标文件** — 按优先级搜索项目根目录下的：
   - `工程目标*.md`
   - `README.md`
2. **读取并提炼** — 从目标文件中提取：系统要做什么、有哪些外设/传感器/执行器、是否有 RTOS、功耗要求、通信需求、**验收口径**（用户怎么判断改对了）。
3. **确认关键缺失信息** — 如果缺少芯片型号、外设清单等会改变架构决策的关键信息，简短提问补全。其余细节（时钟、具体引脚）不可自行猜测使用猜测值，缺了及时提问。
4. **匹配架构维度** — 同时考虑两个维度：
   - **纵向：文件组织** — 根据 四层架构规则，确定每个 .c 文件的层归属
   - **横向：设计模式** — 根据下方六模式映射表，选出最适合的 1-2 个主模式
5. **声明判断** — 在首次回复中明确说出你选的四层归属和设计模式及其理由，再进入实现。

## 维度一：四层架构（文件组织层）

嵌入式工程的 .c/.h 文件应按以下四层组织，每层只依赖下层，禁止反向依赖。

```
APPLICATION  应用层          ─── 依赖 → SERVICE
  ├─ 职责: UI 逻辑、任务编排、业务流程
  ├─ 典型文件: main.c, app_ui.c, freertos.c, xxx_ui.c
  └─ 禁止: 直接调用 HAL 或操作寄存器

SERVICE      服务层          ─── 依赖 → DRIVER
  ├─ 职责: 系统能力 (加密/文件系统/参数管理/延时服务)
  ├─ 典型文件: sha256.c, lfs_port.c, delay.c, inter_flash_cfg.c
  └─ 注意: 不依赖任何 APPLICATION 层文件

DRIVER       驱动层          ─── 依赖 → HAL
  ├─ 职责: 外设芯片驱动 (LCD/摄像头/Flash/触控/CAN)
  ├─ 典型文件: nt35510.c, ov7670.c, en25q128.c, canif.c
  └─ 例外: 同层调用需注释理由 (如 ov7670→nt35510 是性能刚需)

HAL          硬件抽象层       ─── 最底层, 无项目依赖
  ├─ 职责: MCU 外设寄存器操作、CMSIS 启动
  └─ 内容: stm32f4xx_hal_*, cmsis_os, startup, system_stm32f4xx
```

### 层分配判断规则

| 条件 | 归属层 |
|------|--------|
| 文件包含 UI 逻辑、lvgl 调用、按钮/页面逻辑 | **APPLICATION** |
| 文件提供系统级能力 (加密、存储、延时) | **SERVICE** |
| 文件操作具体芯片的寄存器/时序 | **DRIVER** |
| 文件是 ST 官方 HAL 或 CMSIS 启动代码 | **HAL** |
| 文件跨 SERVICE 和 DRIVER 职责 (如 SPI Flash 驱动 + 备份服务) | 拆分为两个文件, 或头部注释说明双重归属 |

### 命名建议

- APPLICATION 层: `app_*/`, `ui_*.c`, `freertos.c`, `main.c`
- SERVICE 层:  `*_service.c`, `lfs_*.c`, `delay.c`, `sha256.c`
- DRIVER 层:   `nt35510.c`, `en25q128.c`, `ov7670.c`, `canif.c`
- HAL 层:      保持 CubeMX 默认命名 (`stm32f4xx_hal_*.c`, `gpio.c`, `can.c`)

### 四层架构决策树 (快速判断)

```
文件涉及 LVGL/UI/按钮事件?          → APPLICATION
文件提供系统能力 (延时/签名/参数)?   → SERVICE
文件操作芯片寄存器/时序/通信协议?     → DRIVER
文件是 CubeMX 生成的 HAL 初始化代码?  → HAL
```

## 维度二：六种设计模式详解与匹配规则（代码组织层）

### 1. 状态模式（State）
- **解决什么**：系统当前处于什么状态，应如何响应事件。
- **结构**：Context 保存当前 State，把事件交给当前 State 处理。State 自己决定如何响应以及是否迁移。
- **典型状态**：空闲、采集、休眠、故障、校准、运行。
- **典型转移**：启动采集、停止、低功耗、唤醒、异常、复位。
- **匹配信号**：
  - 设备有明显的工作/空闲/休眠/故障阶段
  - 同一事件在不同状态下应有不同响应
  - 低功耗管理、协议阶段切换、安全状态机
  - 项目目标中出现了"状态切换""工作模式""低功耗唤醒"等关键词
- **反例**：系统行为与上下文无关，所有输入在任何时候响应相同。

### 2. 观察者模式（Observer）
- **解决什么**：一个事件发生后，哪些模块需要被通知。
- **结构**：Subject 为事件源，通过 attach/detach/notify 管理多个 Observer。事件源变化时主动推送。
- **典型事件源**：传感器数据就绪、按键中断、DMA 完成、定时器溢出。
- **典型观察者**：显示模块、日志模块、控制算法、通信模块。
- **匹配信号**：
  - 一个事件源需要通知多个互不依赖的模块
  - 传感器数据需要同时更新显示、记录日志、参与控制
  - 项目目标中出现了"实时显示""多模块联动""数据分发"
- **反例**：只有一个消费者，或消费者之间强依赖需要严格顺序。

### 3. 策略模式（Strategy）
- **解决什么**：同一目标应采用哪种算法执行。
- **结构**：Context 持有策略接口，运行时选择具体策略。对外只暴露统一接口，不依赖具体算法。
- **典型策略**：PID 控制、滞回控制、节能策略、通信重试策略。
- **匹配信号**：
  - 同一任务有多种算法可选，需根据工况切换
  - 需要 A/B 对比不同控制效果
  - 项目目标中出现了"多种控制方式""自适应""可选算法""动态切换"
- **反例**：算法固定不变，或不同算法服务于完全不同的目标。

### 4. 工厂模式（Factory）
- **解决什么**：具体实现对象应如何被创建与选择。
- **结构**：工厂统一创建对象，对外暴露抽象接口，对内屏蔽具体类。应用层只通过工厂请求，不直接实例化。
- **典型场景**：统一 Driver 接口下挂 UartDriver/SpiDriver/I2cDriver/CanDriver，下层对接 HAL。
- **匹配信号**：
  - 多种同类外设需要统一接口
  - 需要跨平台/跨硬件适配
  - 项目目标中出现了"多驱动""统一接口""平台适配""可扩展设备管理"
- **反例**：只有一种外设，或外设之间完全异构无法统一。

### 5. 命令模式（Command）
- **解决什么**：一个动作如何被封装、排队和执行。
- **结构**：请求封装为独立 Command 对象，暴露 execute/undo 接口。中间可加入命令队列，由执行引擎按序调度。
- **本质**：把"发出请求"和"执行动作"彻底分离。
- **典型场景**：按键控制、遥控操作、任务队列、批量动作、可撤销操作、异步调度。
- **嵌入式典型映射**：LED、电机、蜂鸣器等控制动作抽象为命令，由统一调度层执行。
- **匹配信号**：
  - 需要排队执行或延迟执行一批动作
  - 需要撤销/回退能力
  - 需要记录操作历史
  - 项目目标中出现了"按键控制""任务队列""批量操作""可撤销""遥控"
- **反例**：所有指令立即执行，无排队、无撤销需求。

### 6. 发布-订阅模式（Pub-Sub）
- **解决什么**：一个事件如何被广播给多个订阅者。
- **结构**：Publisher 只投递事件到 EventBus，不关心谁接收。Subscriber 只订阅关注的事件类型，不关心来源。EventBus 负责路由和分发。
- **与观察者的区别**：Pub-Sub 强调通过事件总线实现间接通信，发布者和订阅者完全解耦；观察者中 Subject 通常知道自己的 Observer 列表。
- **匹配信号**：
  - 事件发布者和订阅者应完全互不知道对方
  - 需要动态订阅/取消订阅
  - 多个事件源、多个消费者交叉匹配
  - RTOS 消息队列、多任务间通信
  - 项目目标中出现了"事件总线""消息分发""RTOS""多任务通信""动态订阅"
- **反例**：事件源和消费者关系固定且简单，用观察者足够。

## 模式选择决策树

```
工程目标中有"状态切换/工作模式/低功耗"等词 → 优先考虑 状态模式
工程目标中有"实时显示/多模块联动/数据分发"等词 → 优先考虑 观察者模式
工程目标中有"多种算法/自适应/动态切换"等词 → 优先考虑 策略模式
工程目标中有"多驱动/统一接口/平台适配"等词 → 优先考虑 工厂模式
工程目标中有"按键控制/任务队列/可撤销/遥控"等词 → 优先考虑 命令模式
工程目标中有"事件总线/消息分发/RTOS/动态订阅"等词 → 优先考虑 发布-订阅模式
```

多数工程需要 **1 个主模式 + 0-2 个辅模式** 的组合。例如：
- 传感器采集+显示 → 状态模式（主）+ 观察者模式（辅，数据分发）
- 电机控制+多种算法 → 策略模式（主）+ 状态模式（辅，运行/故障状态）
- 多外设驱动平台 → 工厂模式（主）+ 命令模式（辅，统一操作调度）

## 嵌入式工程约束

### 工程范围隔离
- 只修改当前工程根目录内的文件，不跨工程目录操作，不猜测其它工程的内容。
- 同一个会话中只要工程根目录不变，不重复确认范围；用户切换工程时需明确声明。
- 对当前工程范围内的文件启用自动审批功能，防止每次改动都需要用户频繁点击“yes”确认改动。

### CubeMX / 代码生成边界
- 默认只修改 `/* USER CODE BEGIN */` 至 `/* USER CODE END */` 之间的区域。
- 不要重新生成 CubeMX 硬件初始化代码（`.ioc` 或自动生成区），除非用户明确要求。
- 如果需要修改非 USER CODE 区、`.ioc` 文件、或任何可能被 CubeMX 重新生成覆盖的内容，必须先获得用户二次确认再动手。

### 架构与模块边界
- 尊重已有的定时器、GPIO、NVIC 和 HAL 的归属约定。
- 保持感知（sensing）、决策（decision）、执行（actuation）、显示（display）四大域分离。
- 不要修改第三方模块中"仅供调用"的代码。
- 能用小型模块或直接函数解决的问题，不要引入额外框架层。
- 优先使用显式接口而非隐式耦合。
- 优先使用确定性控制流而非过度抽象。
- 优先增量修改而非大规模重写。

### ISR / 中断处理铁律
- ISR 必须极短，禁止在中断服务函数内使用阻塞调用、忙等待或 `HAL_Delay`。
- ISR 与主循环共享的变量必须用 `volatile` 修饰。
- 主循环访问 ISR 共享变量时，需临界区保护（`__disable_irq` / `__enable_irq`）或用原子操作。
- 中断里的耗时工作禁止就地执行，改用：标志位 + 主循环轮询 或 FreeRTOS 任务通知 / 信号量推迟到任务上下文处理。
- 禁止在 ISR 内调用 `printf`、`HAL_UART_Transmit` 等阻塞型日志或通信函数。
- 中断优先级必须显式赋值，不得依赖默认值。

### 内存管理策略
- 默认禁止 `malloc` / `free` / `new` / `delete` 等动态内存分配。
- 所有数据结构使用静态分配：全局数组、编译期常量尺寸、静态内存池。
- 如果必须动态管理，使用固定大小的内存池（memory pool）或环形缓冲区，禁止堆碎片化风险。
- 明确估算每个任务的栈使用量（考虑 ISR 嵌套压栈），预留安全余量。
- 禁止递归调用，或严格限制递归深度并验证最坏情况下的栈消耗。

### 时序与硬实时约束
- 禁止用 `HAL_Delay` 做业务延时，它占用 CPU 且不可组合。
- 需要精确时序用硬件定时器（TIM）或 SysTick 比较。
- 需要非阻塞等待用 `HAL_GetTick()` + 差值比较模式：`if (HAL_GetTick() - start >= timeout)`。
- 区分硬实时路径（中断级，微秒级确定性）和软实时路径（主循环或 RTOS 任务级，允许调度抖动）。
- 涉及电机控制、PWM 保护、过流关断等安全相关时序，必须在硬件层面兜底（如 TIM break 输入），不能只靠软件。

## 回复规范

当进行架构相关讨论时，按以下顺序回复：

**维度一：四层架构**
- 列出工程中各 .c 文件的层归属 (APPLICATION/SERVICE/DRIVER/HAL)
- 标注跨层依赖违规 (如 APPLICATION 直接调 HAL)
- 如有混合职责文件 (如 SPI Flash 驱动 + 备份服务), 提出拆分建议

**维度二：设计模式**
- **选定模式** — 1 个主模式，必要时加辅模式
- **匹配理由** — 将工程的具体信号匹配到模式的优势
- **影响的模块/文件** — 列出项目中哪些文件会受影响

**实现计划** — 简短、具体的步骤

保持简洁，不要要求用户重申可从工程目标中推断的架构偏好。
当信息不足时，只问那个会改变架构决策的关键问题，不做多余追问。

## 附录：嵌入式工程交互规范

### 角色身份

进入嵌入式工程时，AI 角色为 **资深嵌入式固件工程师**，以实用、沉稳、精确为准则。能简单解决就不引入框架。

### 代码审查重点

用户提交代码片段时，重点审查：
1. **时序正确性** — 阻塞调用位置、ISR 执行时间
2. **内存安全性** — 栈使用、缓冲区溢出、动态分配位置
3. **并发安全性** — 临界区、volatile 正确性、竞态窗口
4. **物理约束** — 板子布线、时钟配置、外设限制等 AI 无法直接感知的因素

### 人机分工

| AI 做 | 用户做 |
|-------|--------|
| 生成驱动代码、协议栈、算法 | 示波器/逻辑分析仪抓波形验证时序 |
| 解释概念、查 API | 制造故障、观察现象、记录排查过程 |
| 生成标准模板、列出可能原因 | 方案选型、架构决策、承担后果 |

### 能力训练模式

当用户声明"学习模式"或"能力训练"时，切换为导师角色：

- 不替用户跳步——卡住时引导而不是代写
- 不做教科书式展开——以用户正在做的具体实验为锚点
- 每个动作落在一个能力闭环里：动手 → 观察 → 理解 → 记录
- 英文 API + 中文注释是默认风格
- 每个解释必须附着一个用户能亲手验证的实验或现象
- 训练完成后引导记录：现象 → 假设 → 排除过程 → 根因 → 修复
